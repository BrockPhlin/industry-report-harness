# 第11组中期展示讲稿

共7分钟，真实联调结果见中期验证记录。

## 第1页　产业智能报告生成系统（约20秒）

大家好，我们是第11组。开题时，我们计划做一套产业报告系统。根据老师的反馈，这次先把范围缩到一份光伏产业简报。接下来我会讲为什么选这个案例、参考的框架用在哪里、程序怎么查证据，以及我们现在验证到了哪一步。

## 第2页　中期只做一份光伏产业简报（约45秒）

开题时我们计划覆盖不同产业和多种报告类型。中期先用光伏，因为两份公开资料的口径不同，能检验系统会不会把两个指标混写。比如一个数是组件制造出来多少，另一个数是新建发电设施装了多少。我们把任务定成两个章节，读者可以从每个数据回到原文。做完这一步，再谈复制到其他行业。

## 第3页　框架参考落到了代码里（约50秒）

这里讲清楚我们各参考了什么。DeepSeek Harness 用 SDK 发起会话，通过 MCP 调用我们自己的光伏证据工具。Pi CLI 用自定义扩展调用同一个工具，还把记录以 JSON 输出。两个框架都实际运行过，但它们连接的是本地模拟模型。当前业务主程序用 Python 的 LangGraph，负责控制哪一步做什么。DeepSeek 的 chat-demo 提供文件输入和 Markdown 展示的交互参考，本轮的审阅入口是命令行。

## 第4页　Agent 每写一章，先找这一章的证据（约55秒）

用制造这一章举例。模板要求有组件产量，也要有组件价格变化。模型先发一条查资料请求，工具返回对应的证据和官方原文位置。流程自己看是不是还有指标没拿到，如果缺一个，就再查一次。数字和单位直接从那条证据填进去。模型可以帮助解释口径，审阅的人仍然可以回到原文核对，修改说明，再确认导出。这样我们能够解释每个数字是怎样进入报告的。

## 第5页　我们故意拿掉一份资料（约80秒）

我先打开缺资料的真实联调记录。这里保留了工信部资料，把国家能源局的资料移出。装机这一章首次查询为空，补查一次还是空，草稿就标记为待核实。再看导出的 PDF，制造数据仍有出处，装机一栏也保留了待核实提示。现场可以用离线模式重现同一条判断路径。

操作提示：先展示缺资料用例的检索与补查记录，再打开 GLM 缺资料 PDF。

## 第6页　完整资料三项可复核，缺资料留一项待核实（约45秒）

真实模型联调采用 GLM-5.3-Flash。完整资料里有三个指定指标，数字、单位和出处逐项对得上。故意移除装机资料后，程序补查一次，仍然缺资料，就把这一项标为待核实。我们还跑了二十五项自动测试。两次联调用来确认流程，后续要扩大样本才能评价普适性。

## 第7页　由六人交接 Agent 的各个环节（约45秒）

分工按一条 Agent 任务来安排。先由组长和需求同学确认每章需要哪些指标。资料同学交给编排同学的是有口径和定位的证据条目。审阅同学用同一个结果核对，测试同学再故意删掉一份资料验证缺项。我们会用任务记录保存实际交接、复核和修改。目前这些责任和时间是拟议安排，周一课后在小组讨论确认。 这次已经用上了开题保留下来的课件映射和公开样例，相关提交能回查。

## 第8页　中期计划收敛为一条可验证流程（约40秒）

对照开题计划，原来同时安排了多个产业、多种报告和多种版式。我们先做光伏，把证据、缺项和导出这三件事跑完整。现在离线和真实模型的流程都留下了记录。中期前剩下的是组员一起复核样张，并按正式时间彩排。

## 第9页　下一步验证稳定性和按章恢复（约40秒）

相比开题，我们已经从录入和摘录走到按章节找资料、说明缺项，以及核对后导出。两组真机样例跑通以后，接下来会补更多失败用例，并保存每章的执行进度，避免一次失败就重跑整份文稿。之后再用另一个能源案例检验模板能不能复用。
