# 第11组中期展示讲稿

全程7分钟。演示环境使用离线决策和公开资料。

## 1　产业智能报告生成系统（20秒）

大家好，我们是第11组。开题时，我们计划做一套产业报告系统。根据老师的反馈，这次先把范围缩到一份光伏产业简报。接下来我会讲为什么选这个案例、参考的框架用在哪里、程序怎么查证据，以及我们现在验证到了哪一步。

## 2　中期只做一份光伏产业简报（45秒）

开题时我们计划覆盖不同产业和多种报告类型。中期先用光伏，因为两份公开资料的口径不同，能检验系统会不会把两个指标混写。比如一个数是组件制造出来多少，另一个数是新建发电设施装了多少。我们把任务定成两个章节，读者可以从每个数据回到原文。做完这一步，再谈复制到其他行业。

## 3　框架参考落到了代码里（50秒）

这里讲清楚我们各参考了什么。DeepSeek Harness 用 SDK 发起会话，通过 MCP 调用我们自己的光伏证据工具。Pi CLI 用自定义扩展调用同一个工具，还把记录以 JSON 输出。两个框架都实际运行过，但它们连接的是本地模拟模型。当前业务主程序用 Python 的 LangGraph，负责控制哪一步做什么。DeepSeek 的 chat-demo 提供文件输入和 Markdown 展示的交互参考，本轮的审阅入口是命令行。

## 4　Agent 每写一章，先找这一章的证据（55秒）

用制造这一章举例。模板要求有组件产量，也要有组件价格变化。模型先发一条查资料请求，工具返回对应的证据和官方原文位置。流程自己看是不是还有指标没拿到，如果缺一个，就再查一次。数字和单位直接从那条证据填进去。模型可以帮助解释口径，审阅的人仍然可以回到原文核对，修改说明，再确认导出。这样我们能够解释每个数字是怎样进入报告的。

## 5　我们故意拿掉一份资料（80秒）

现在展示一个缺资料的用例。我们把国家能源局的资料从这次任务里移除，只保留工信部的制造数据。先运行命令生成草稿，再打开调用记录。发电新增装机这一章第一次查不到，系统补查一次，还是没有。到这里流程停止查找，不会用组件产量填上去。我们再看 PDF，制造数据还在，新增装机仍然标为待核实。现场这条用例用固定的离线决策，方便每次重跑。

操作顺序见[中期验证记录](../evidence/README.md)，使用缺少国家能源局资料的任务。

## 6　完整资料三项可复核，缺资料留一项待核实（45秒）

完整样例里，我们核对了三个指定指标，三项都能定位到原文。开题的摘录基线用的是同一份输入，它把内容列出来。现在可以看到内容进了哪一章、查过什么、哪些证据没有找到，也能确认后导出。我们同时跑了18项基线测试和7项中期测试。这些结果说明流程和接口按预期工作。真实模型效果还需要用相同输入再测一遍。

## 7　由六人交接 Agent 的各个环节（45秒）

分工按一条 Agent 任务来安排。先由组长和需求同学确认每章需要哪些指标。资料同学交给编排同学的是有口径和定位的证据条目。审阅同学用同一个结果核对，测试同学再故意删掉一份资料验证缺项。我们会用任务记录保存实际交接、复核和修改。目前这些责任和时间是拟议安排，周一课后在小组讨论确认。 这次已经用上了开题保留下来的课件映射和公开样例，相关提交能回查。

## 8　中期计划收敛为一条可验证流程（40秒）

我再用开题计划和实际进度对一下。原来同时安排多个产业、多个报告类型和多版式。根据老师反馈，我们先做光伏单一案例，把证据、缺项和导出跑完整。现在这条离线流程已经有验证记录。真实模型联调和组内彩排是中期前的剩余项。确认真实调用结果后，我们会再更新汇报里的状态。

## 9　下一步用真实模型验证，再做按章恢复（40秒）

相比开题，我们已经从录入和摘录，走到一份简报可以按章节找资料并解释缺项。接下来第一件事是接真实 GLM，用同样的完整和缺失用例逐条人工核对。第二件是保存每章的执行进度，让一次失败不至于重跑整份文稿。等这两步能复现，再加一个能源案例检验模板复用。到这里就是我们的中期进展。
