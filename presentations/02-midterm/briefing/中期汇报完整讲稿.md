# 第11组中期汇报完整讲稿

主讲人 **程文博**。按六段组织，计划讲约 6 分 40 秒，留 20 秒给停顿和样张切换。括号中的时长供彩排计时。正文经 AI Studio 中的 Gemini 4 Neon 审阅，再按运行证据核对和修改。

## 1. 为什么先做光伏（约45秒）

各位老师、同学好，我是第11组的程文博。开题时，我们想做一个能生成多类产业报告的系统。老师建议我们先收窄范围，把一个真实案例做清楚。所以中期我们先做2024年中国光伏产业简报，只写两章。一章看组件制造和价格，另一章看发电新增装机。

这两章里有两个容易混在一起的数字。工信部公布的588吉瓦，是当年生产了多少光伏组件。国家能源局公布的2.78亿千瓦，是当年新增了多少光伏发电装机。我们想先让报告里的数字能查回原文。资料不够时，读者也要能看出来。

## 2. 我们怎么参考开源 Harness（约55秒）

老师还问过，我们有没有看过主流框架。我们选了 DeepSeek Harness 和 Pi CLI，给它们接入同一个只读资料工具，去查新增装机。DeepSeek Harness 通过 MCP 接工具。Pi 用扩展注册工具，终端能看到工具开始和结束的事件。两次实验都用本地模拟模型，我们确认了工具查到的证据能进下一次模型请求。chat-demo 也看过，它的附件交互和 Markdown 展示可以作为后续界面参考。

我们借鉴了两点：把查资料做成独立工具，以及把每次查询和补查记下来。简报用 Python 和 LangGraph 编排章内步骤，因为补不补查可以按固定规则判断，换掉一份资料也容易复测。真实联调用的是 GLM-5.3-Flash。

## 3. 一份简报怎样生成（约70秒）

以发电新增装机这一章为例。模板先写明这一项必须查。模型提出查找请求，资料工具返回统计期、数值、单位和原文位置。系统比较模板和已拿到的证据，缺哪项，就在输入的资料里补查哪项。还是找不到，简报写“待核实”。

数字、单位和口径容易在改写时被带偏。所以数值和单位由程序从证据填入，口径说明从模板读取。模型可以写一段辅助观察，留给人核对。研究员拿到 Markdown 草稿后，可以修订文字，确认后再导出 PDF。数值、出处或待核实标记被误改时，程序会拦住导出。

## 4. 两份样张能看出什么（约105秒）

请看两份用真实 GLM 生成并导出的样张。第一次把工信部和国家能源局的资料都给系统。制造与价格章有组件产量和价格变化，装机章能查到2.78亿千瓦，三项都有出处。第二次只拿掉国家能源局的资料，其他输入保持相同。系统查了一次，又专门补查装机，还是没有结果。最后导出的报告留下一个“待核实”，工信部那两项制造数据和出处都还在。

我们这样测，是因为一份报告看起来写得越完整，越容易让人忽略哪些资料其实没找到。把缺项留在最终 PDF 里，研究员读到这一段就知道还缺什么。另外，长报告写到一半就停，前面写好的章节如果也得重跑，会多等一轮。我们用真实 GLM 完成第一章后主动停掉程序。重启以后跳过第一章，接着写完并导出。这次测的是程序中断后的恢复。

## 5. 六个人怎样交接（约80秒）

老师希望我们围绕智能体流程分工。下面用装机指标说一下这次的准备安排。田亦洁负责确认每章必查什么和怎么验收，崔大元负责把指标和原文位置整理好，许子萌把它接到资料工具和模型流程里。李佳雨核对草稿和导出的报告，郭润航用完整和缺资料两种输入独立复跑。我负责定范围、协调交接、验收和今天的汇报。

大家交接时要能说出同一条资料的来路。比如崔大元交出装机指标和原文位置以后，测试可以用这个来源编号排除资料，再去看运行记录和导出结果。这样发现问题，就能定位是资料没收到、流程没补查，还是导出时少了标记。

## 6. 后续怎么验收（约45秒）

中期先交付这份光伏简报。封版后，我们又用固定样例验证了资料冲突、客户端超时和风电复用。下一步想试一个参考报告检索工具。研究员写新报告时往往先看同行怎么组织章节，我们想让工具给模型几条可回查的结构参考。事实仍从本次资料取。用同一批资料各跑一遍，看看开和不开这个工具，结构修改量和事实错误有没有变化。

我们希望最终交给人的，是一份能审、能改、能说明资料从哪里来的报告。谢谢大家。
