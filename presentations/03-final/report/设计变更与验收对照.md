# 2　任务流程与失败处理

## 2.1　一次任务怎样运行

1. `load_inputs` 读取章节模板和人工摘编。模板列出每章的必查指标。资料为每条数值指定统计期、单位和来源编号。来源表记录原文网址及可定位的位置。
2. `section_graph` 用 LangGraph 依次执行检索、补查和草稿节点。检索按指标编号取资料，缺失的指标会用同一份资料库补查一次。对于同一指标，统计期、数值、单位的任一字段表述有差异时，程序保留候选记录。写作模型只收到可采用的记录，候选数值和出处由程序写入报告。
3. `RunCheckpoint` 每完成一章便保存结果。恢复时用输入指纹核对模板、资料、模式和模型配置。程序重查已保存章节的记录结构与证据，随后只继续未完成的章节。整份草稿生成后，任务目录才会发布。
4. `approve_run` 核对生成时保存的指标、待核实标记、候选来源和章节位置。用户确认后，Typst 生成 PDF。命令行确认表示完成此次导出操作，未解决的资料分歧仍由研究人员判断。

## 2.2　失败怎么处理

| 情况 | 程序的处理 |
| --- | --- |
| 资料缺失 | 补查一次，仍无结果就保留待核实标记。 |
| 资料表述不一致 | 同时列出候选值和位置，保留原字段。等人工核对口径后更新输入，重新生成报告。 |
| 模型超时或连接中断 | 提示中断的章节及步骤，保留已完成的章。使用原输入追加 `--resume`，未完成章从头运行。 |
| 检查点与输入不匹配或文件损坏 | 终止操作并提示使用新的任务目录，保留原记录供排查。 |

两次超时实验验证了不同情形。本机 HTTP 测试控制第二章写作正文延迟，观察恢复后第一章的请求数。真实 GLM 联调将客户端等待设为 0.1 秒触发首章超时，再恢复默认时长跑完。真实联调验证的是客户端处理流程，未观测到服务商自然故障。
